How the fraud detection pipeline works

From raw transactions to a ranked alert queue, in six steps. Each step is a module in the repository and is covered by tests.

1. Real, labelled data

IEEE-CIS holds 590,540 e-commerce transactions from Vesta over about six months, with more than 400 columns: amount, product code, card and address fields, email domains, device data, counting features (C1 to C14), time deltas (D1 to D15) and 339 engineered Vesta features. A separate identity table covers 24% of transactions, and those transactions have a fraud rate of 7.85% against 2.09% without one. ULB holds 284,807 European card transactions from two days in September 2013, whose 28 features are PCA components, so it tests whether the decision rule generalises to a very different fraud profile.

2. Out-of-time validation

Random train/test splits leak the future into training and overstate performance. Every split here is by time:

  • IEEE-CIS: train on days 1 to 119, tune on days 120 to 151, report on days 152 to 182.
  • ULB: train on hours 0 to 29, tune on hours 30 to 38, report on hours 39 to 47.

Thresholds and policies are chosen on the validation period and applied unchanged to the test period.

3. Features fitted on training data only

Frequency encodings for high-cardinality fields such as card1 and email domain, and a customer proxy built from card, address and the account-start date (card1 + addr1 + (day − D1)). Per-customer means and standard deviations of amount, distance and counting features let the model ask "is this unusual for this customer?" All statistics come from the training months, so no information leaks from the future.

4. LightGBM against a baseline

A gradient boosted tree model (LightGBM, early stopping on log loss, no class reweighting so probabilities stay calibrated) is compared with a regularised logistic regression. On IEEE-CIS the test PR-AUC is 0.573 for LightGBM against 0.164 for the baseline. Train PR-AUC is 0.99, so the model does overfit; the out-of-time test numbers are the honest ones.

5. A decision rule based on cost

A probability is not a decision. The production rule alerts on a transaction when

p(fraud) × (amount + chargeback fee)  >  review cost

so a $2,000 order is reviewed at a much lower probability than a $10 one. With a $15 chargeback and a $5 review, this rule cost $138,481 on the test month against $172,751 for the best single threshold and $409,060 for the usual 0.5 cut-off. See it for yourself in the threshold calculator or read how to choose a threshold by cost.

6. Serving and monitoring

  • Scoring API: FastAPI POST /score returns the probability, the alert decision, the expected loss and the top three reasons from SHAP values.
  • Alert queue: a Streamlit dashboard ranks alerts by expected loss, lets analysts change costs live and records confirm or dismiss decisions.
  • Model registry: each training run writes metadata with the git commit, costs, thresholds and test metrics.
  • Drift check: the population stability index and mean score shift against a training reference; the job exits non-zero when drift crosses the alert level.
  • Delivery: Docker and docker-compose for the API and dashboard, and GitHub Actions running the tests on every push.
